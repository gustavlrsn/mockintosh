# Plan 9 design research

Research date: 2026-09-10. Primary sources are the original Bell Labs papers and Plan 9 manuals. Historical papers describe earlier editions; the protocol details below follow the 9P2000 manual.

## Core concepts

**A personal computing environment assembled from services.** Plan 9 combines three ideas: resources exposed through file hierarchies, one protocol for accessing those services, and a private namespace that joins their trees. The original system separated terminals, CPU servers, and storage servers. Its goal was to make a user's environment portable across that network, with familiar names resolving to the appropriate resources. The architecture matters more than its visual appearance. [Plan 9 from Bell Labs](https://9p.io/sys/doc/9.html)

**Files are interfaces, not necessarily stored documents.** A service exposes discoverable names and operations such as open, read, and write; its files can represent devices, running processes, or live controls. Kernel-local services can implement the corresponding operations through direct calls, without serializing every access into a network packet. Plan 9's kernel is described as a traditional kernel, despite extensive use of user-space file servers. [The Use of Name Spaces in Plan 9](https://9p.io/sys/doc/names.html)

**Namespaces belong to processes, with sharing when wanted.** `bind` and `mount` modify the caller's namespace group. `bind` exposes an existing resource under another name; `mount` attaches a file service through a connection. Replacement hides an earlier binding; `-b` and `-a` put a directory before or after existing entries in an ordered union. Creation targets must be explicitly designated with `-c`. These are resource-routing operations, not copies of file contents. [bind(1)](https://9p.io/magic/man2html/1/bind)

**9P provides a small, stateful service vocabulary.** The 9P2000 protocol specifies attach, walk, open, create, read, write, clunk, remove, stat, and related operations. A `fid` identifies a client's reference to a server-side resource; it is distinct from the resource's `qid` identity. Requests carry tags, permitting concurrent operations and out-of-order responses. Reads may remain pending until external events occur. `Tflush` provides cancellation. A path-to-JSON router captures only part of these semantics. [9P2000 protocol introduction](https://9p.io/magic/man2html/5/intro)

**Window interfaces can themselves be services.** Rio exposes window text, label, mouse, clipboard (`snarf`), image, and control files. Writing `wctl` can move or resize a window; later reads block until its state changes. Window-specific virtual devices appear in each window's environment. Rio can run recursively. A useful detail: rio positions windows, but the draw device multiplexes graphics access itself. [rio(4)](https://9p.io/magic/man2html/4/rio)

**Applications can be extended from outside.** Acme exposes per-window `body`, `addr`, `data`, `ctl`, and `event` files. An external program can inspect and edit text, select an address, and interpret user actions through the event interface. Extension consequently need not mean loading code into the editor's process. Opening `event` changes handling of certain user actions, so this interface is more than a passive notification feed. [acme(4)](https://9p.io/magic/man2html/4/acme)

**The plumber makes contextual text actionable.** Programs send structured messages to `/mnt/plumb/send`; rules inspect and rewrite them, route them to named ports, or start a handler. A filename plus line number can open an editor at that location. The system centralizes interpretation that applications would otherwise duplicate. It is distinct from a generic event bus: contextual message matching and routing are its central behavior. [Plumbing and Other Utilities](https://9p.io/sys/doc/plumb.html)

**Factotum separates credential handling from applications.** The authentication agent holds and uses keys on a user's behalf, exposing its service through files. Authentication protocols can change in that component without being embedded in every client. The security paper also explicitly separates authentication from 9P and discusses encrypted transport as another component. This is architectural inspiration, not a recommendation to reuse historical cryptography. [Security in Plan 9](https://9p.io/sys/doc/auth.html)

## Avoid misleading simplifications

- A global virtual filesystem alone misses the private-namespace composition mechanism. Sharing a namespace is a choice, not the definition of the architecture. [bind(1)](https://9p.io/magic/man2html/1/bind)
- “Everything is a file” does not imply everything is plain text, persistent, seekable, or side-effect-free. Rio's image and control files illustrate different contracts. [rio(4)](https://9p.io/magic/man2html/4/rio)
- Namespace substitution isolates name resolution; it does not inherently copy underlying state or supply a complete security boundary. This is an inference from bind's aliasing semantics. [bind(1)](https://9p.io/magic/man2html/1/bind)
- A uniform remote interface does not eliminate latency, pending operations, cancellation, or failures. Those concerns remain explicit in 9P's transaction model. [9P2000 protocol introduction](https://9p.io/magic/man2html/5/intro)

## Review of Mockintosh's kernel plan

Historical review: this section examines the earlier namespace/RPC/process/shell plan. The [current kernel plan](kernel-plan.md) was subsequently rewritten around editable agent-built apps and live MCP control, incorporating these findings. Its milestone sequence and current-checkout notes supersede the recommendations and observations below.

The following are design recommendations based on this checkout, not claims about features already implemented. The working tree contains ongoing app/window changes; the kernel plan should be reconciled with those before implementation. Sources: [kernel plan](kernel-plan.md), [architecture](../ARCHITECTURE.md), [project ideas](ideas.md).

The plan's strongest choices are the mounted persistent volume, synthetic services over existing state, named UI inspection, shared input injection, and a small kernel interface. Keep the typed SDK and efficient rendering paths. The purpose of exposing services is to make them inspectable and composable, not to make every internal property or drawing operation a text file.

### Changes to make before implementation

1. **One naming model, multiple namespace views.** Replace the implication of one global mount table with a shared default namespace and explicit caller/session context. Add namespace cloning and replacement bindings when the first device-substitution demo needs them; full process accounting can follow. A process can see a virtual printer at `/dev/printer` while another sees the physical one. Keep service identity separate from the paths under which it is mounted. With aliases, `pathOf(id)` needs a namespace and a preferred-path policy; it cannot be the unique inverse of resolution. See the existing id-based [FileSystem](../packages/fs/src/fileSystem.ts).

2. **Define service contracts beyond filenames.** Distinguish snapshot data, control writes, and event streams. Specify formats, atomic command boundaries, errors, and cleanup. Begin with whole-file convenience methods, but leave room for open/read/close handles and cancellable pending reads. An event subscription needs its own cursor and a stated overflow policy. This is useful before implementing the actual 9P wire format.

3. **Fix the remote projection assumptions.** `watch(path, callback): Unsubscribe` is not JSON-serializable. RPC needs subscription IDs, notifications, unsubscribe, and disconnect cleanup. Async wrappers around synchronous `stat`/`children` do not enable uncached remote metadata: use an explicit reactive cache with loading/error/staleness states, or allow async metadata in the service interface and let the GUI project it into that cache. Compare operations and outcomes across local and RPC clients; merely enumerating mounts cannot prove facade parity. These issues are visible in the proposed interfaces in [kernel-plan.md](kernel-plan.md).

4. **Treat UI addresses as identities, not just positions.** Removing an earlier sibling can make `button.1` identify a different surviving button; it will not necessarily produce the promised `ENOENT`. Use stable node identities or generation-checked references for actions, and explicit handling of duplicate names. A centre-point click can hit an occluding window, or only activate an inactive one under the current Mac input policy. Define visibility, activation, and stale-target outcomes while retaining the shared input path. See [window activation rules](../ARCHITECTURE.md).

5. **Reconcile process design with current app ownership.** The checkout already has `AppContext`, `createAppContext`, and `SolidApp.onOpen`; build process ownership around that seam rather than an older component-only model. Namespace filtering cannot sandbox same-realm JavaScript with ambient browser access. Real containment requires an execution boundary and mediated host capabilities. Solid ownership also requires explicit cleanup of host timers; it does not cancel arbitrary timers automatically. Sources: [appContext.ts](../src/os/appContext.ts), [SDK](../packages/sdk/src/index.ts), [PhotoBooth](../apps/PhotoBooth.tsx).

6. **Make time and replay promises precise.** Headless `tick` advances frame callbacks, while the platform still permits host timers. A displayed-frame wait can hang on an idle desktop because boot deliberately presents only dirty frames. Specify a render barrier or scheduler-turn operation separately from waiting for actual presentation. Record/replay additionally needs controlled timers, random values, and external input; writing a mutation log alone does not provide deterministic replay. Sources: [headless platform](../src/platform/headless/index.ts), [boot tests](../src/os/boot.test.ts), [platform contract](../src/platform/types.ts).

### Playful directions

**Virtual peripherals in the Chooser — first experiment.** Give a printing app a binding to a paper printer, scrapbook printer, or simulated fax service. Each accepts the same documented page format; the selected provider changes the result. Add an Inspector showing the active path, provider, input, and output. Start with print because the [printing service](../src/os/printing.ts) already supplies a host boundary. Camera substitution comes later: [PhotoBooth](../apps/PhotoBooth.tsx) currently captures through browser APIs directly and needs a camera-provider seam first.

**Apps as construction kits.** A drawing toy could serve `document`, `selection`, `ctl`, and `events` beneath `/apps/<instance>/`. An external helper mirrors the selected shape, adds a border, or makes a contact sheet without loading a plugin into the drawing app. These are proposed paths. Expose semantic document operations as well as the UI tree: clicking a button is good for exercising the UI, while updating a shape is better for composition. This applies the Acme extension model described above.

**A Macintosh plumber.** Extend [openers.ts](../src/os/openers.ts), which currently selects handlers by MIME type, into contextual routing. An Open Selection action can send a filename and line number to an editor, a picture reference to Picture, or a game clue to a decoder. Rules can be editable documents. Preserve document identity and namespace context when delivering references across processes; a sender's local pathname may resolve differently for its recipient.

**Worlds on floppies.** A cartridge folder contains documents, a HyperCard-style interface, service definitions, and routing rules. Inserting it mounts a small world: a fictional inbox, radio, archive, printer, and tools. Progress in the resistance game from [ideas.md](ideas.md) can mean acquiring a new service or changing a binding. A writable session layer can support Reset World, but needs explicit overlay/copy-on-write semantics; a Plan 9 union alone is not an undo mechanism. A restricted interpreter would make simple cards usable before a full in-OS TSX compiler.

**A networked toy workbench — later.** Export a selected service tree from another Mockintosh instance and mount it locally: shared scrapbook, pen-pal mailbox, remote printer. Start with a read-only tree, then add explicitly designed write/conflict behavior. The existing RPC proposal is remote control; importing the remote tree into the local VFS is the additional compositional step. A desktop inside a desktop is another appealing rio-inspired experiment, but the documented single-instance renderer and QuickDraw globals mean a second boot in the same realm is not currently free.

### Suggested order

Keep the instruction to land the platform refactor separately. Then deliver a narrow namespace slice with named UI inspection and an Inspector/command field; demonstrate two interchangeable printer providers; add contextual Open Selection and one externally extensible drawing/card toy. Expand process lifetimes, streaming, and the remote surface as these examples require them. Retain MCP early if agent access is the immediate priority, but do not make humans wait for the entire shell milestone to experiment. Implement 9P interoperability only when connecting to real 9P clients becomes a goal.

The first product acceptance test should be: **change an app's printer binding and see the same Print action produce paper, a scrapbook entry, or a simulated fax, without editing the app.** This tests the Plan 9 composition idea and delivers an enjoyable feature at the same time.
